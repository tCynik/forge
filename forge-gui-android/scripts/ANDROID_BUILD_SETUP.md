# Синхронизация сборки/деплоя Card-Forge Android между двумя машинами

> Этот файл живёт **только** в ветке `tooling-sync` (см.
> `TOOLING-SYNC-DO-NOT-MERGE.md` в корне репозитория на этой ветке) и никогда
> не должен попадать в `master` или рабочие ветки — как и сами скрипты рядом
> с ним. В релиз не должны попадать временные локальные инструменты.

Цель: одинаковые скрипты сборки, один и тот же подписывающий ключ, одна
методика деплоя на двух машинах — без обнуления игрового прогресса при
переключении между ними.

Подробное обоснование ("почему именно так") каждого шага — в `CLAUDE.md` в
корне репозитория, раздел "Android device build/deploy" (там же описан этот
файл и подход с веткой `tooling-sync`). Здесь — практическая выжимка + чеклист
синхронизации. Сверено с фактическим кодом `Common.ps1`/`Build-Deploy.ps1`/
`Push-LocalRes.ps1` на этой ветке.

## 0. Как устроена синхронизация через эту ветку

**Не переключайте основной рабочий репозиторий на `tooling-sync` через
`git checkout`.** Скрипты в этой ветке — трекнутые файлы; в рабочих ветках их
нет вообще. Обычный `git checkout tooling-sync` в основной рабочей копии, а
затем `git checkout <рабочая-ветка>` обратно, **удалит** файлы скриптов с
диска при обратном переключении (git убирает файлы, трекнутые в ветке, откуда
уходишь, если их нет в целевой ветке) — ровно то, чего мы хотим избежать.

Вместо этого — **git worktree**: отдельная папка рядом с основным репозиторием,
постоянно выставленная на `tooling-sync`, не зависящая от того, какая ветка
выставлена в основной рабочей копии.

### Разовая настройка на каждой машине

```powershell
cd <куда угодно, скрипт сам найдёт корень репы>
git -C <путь-к-основному-репо> fetch origin tooling-sync
git -C <путь-к-основному-репо> worktree add ../forge-tooling-sync tooling-sync
```

(если ветки `tooling-sync` ещё нет локально — `git worktree add -b
tooling-sync ../forge-tooling-sync origin/tooling-sync`).

Теперь `../forge-tooling-sync` — постоянная папка с этой веткой. Основной
репозиторий как был на рабочей ветке, так и остаётся ей все время.

### Синхронизация (когда что-то изменилось на одной из машин)

**На машине, где что-то поменяли** (например, доработали `Build-Deploy.ps1`):

```powershell
cd ../forge-tooling-sync
# скопировать актуальные версии файлов из рабочего репо (если правки делались
# прямо в forge-gui-android/scripts/ основного репо, а не тут):
Copy-Item ..\forge\forge-gui-android\scripts\*.ps1 forge-gui-android\scripts\
git add forge-gui-android/scripts
git commit -m "..."
git push origin tooling-sync
```

**На второй машине** (забрать изменения и положить их туда, где их видят
build-скрипты — в `forge-gui-android/scripts/` основного репозитория,
где они **не трекаются git** и потому не мешают ни одной рабочей ветке):

```powershell
cd ../forge-tooling-sync
git pull
Copy-Item forge-gui-android\scripts\*.ps1 ..\forge\forge-gui-android\scripts\ -Force
```

Файлы в основном репо остаются untracked (см. раздел 1 про `.gitignore`) —
это нормально и намеренно: git в основном репо про них ничего не знает, они
просто лежат на диске и используются локально.

## 1. Что попадает в git на этой ветке, а что нет

| Файл/папка | В git на `tooling-sync`? | Почему |
|---|---|---|
| `Common.ps1`, `Build-Deploy.ps1`, `Push-LocalRes.ps1` | Да | Это и есть то, что синхронизируем |
| `ANDROID_BUILD_SETUP.md` (этот файл) | Да | Инструкция едет вместе со скриптами |
| `.device-state.json` | Нет (`.gitignore` на этой ветке) | Кэш "какое устройство использовалось последним" — per-машина, на другой машине бессмысленный/вредный |
| `backups/**` | Нет (`.gitignore` на этой ветке) | Реальные бэкапы игрового прогресса, которые скрипт делает сам при каждом деплое — не артефакт тулинга |
| `%USERPROFILE%\.forge-android-build\debug.keystore` (подписывающий ключ) | **Никогда, ни на одной ветке** | Приватный ключевой материал; хранить в git-истории нельзя даже в приватном форке — см. раздел 3 |

## 2. Что понадобится установить (на каждой машине отдельно, не синхронизируется)

| Что | Зачем | Где взять |
|---|---|---|
| **JDK 17** | Корневой `pom.xml` фиксирует `maven.compiler.release=17`; более новый JDK (напр. 23) не подходит для Android-тулчейна | IntelliJ IDEA сама предложит скачать в `~/.jdks/`, либо отдельно (Temurin/Corretto 17) |
| **Android SDK** | `platform-tools` (adb), `build-tools;35.0.0`, `platforms;android-35` | Android Studio → SDK Manager, либо `sdkmanager` |
| **Maven 3.8.1** | Форкнутый `android-maven-plugin:4.6.2` требует именно её | Не обязательно ставить — скрипт сам найдёт IntelliJ-bundled `mvn.cmd` (там 3.8.1) |
| **git, PowerShell** | Клонирование, запуск скриптов | — |

`Get-BuildJavaHome` / `Get-MvnCommand` в `Common.ps1` сами резолвят JDK17/Maven
локально на каждой машине — версии инструментов не обязаны совпадать
байт-в-байт, только соответствовать требованиям выше.

`adb` должен быть на `PATH`:
```powershell
$env:PATH = "$env:LOCALAPPDATA\Android\Sdk\platform-tools;$env:PATH"
```
(добавить в постоянный `PATH` через "Переменные среды" Windows).

## 3. Подпись APK (keystore) — обязательная разовая ручная синхронизация

Это **главная причина**, по которой прогресс обнулялся при переключении
машин, и единственный элемент синхронизации, который **нельзя** делать через
git.

- Сборка идёт с профилем `android-test-build` (не `android-debug` — у того
  встроенный signer ломается под JDK17). Профиль оставляет APK неподписанным.
- После сборки `Build-Deploy.ps1` сам переподписывает APK
  (`tools/uber-apk-signer.jar --allowResign --overwrite --ksDebug <keystore>`)
  keystore'ом, закреплённым по пути `%USERPROFILE%\.forge-android-build\debug.keystore`
  (`Get-PinnedDebugKeystore` в `Common.ps1`).
- При первом запуске на машине, где такого файла ещё нет, скрипт сам создаёт
  его (копирует `~/.android/debug.keystore`, если есть, иначе генерирует новый
  через `keytool`) — то есть **если этот шаг пропустить, каждая машина
  сгенерирует себе свой ключ, и проблема с обнулением прогресса вернётся**.

### Разовый перенос ключа между машинами

1. На машине, где уже стоят актуальные установки на устройстве(-ах), найти
   `%USERPROFILE%\.forge-android-build\debug.keystore`.
2. Скопировать этот файл на вторую машину, в тот же путь, **любым каналом
   кроме git** (флешка, облако, scp).
3. Проверить, что файл действительно один и тот же на обеих машинах (см.
   ниже) — не полагаться на "скопировал и вроде норм".

### Проверка корректности ключа (сверка отпечатка)

На каждой машине:
```powershell
keytool -list -v -keystore "$env:USERPROFILE\.forge-android-build\debug.keystore" -storepass android
```
Сравнить строку `SHA256:` в выводе на обеих машинах — **отпечатки должны
совпадать побайтово**. Если не совпадают — файл разошёлся (скопирован не тот,
или на одной из машин ключ успел пересоздаться до переноса) — повторить
разовый перенос из предыдущего пункта, взяв файл с машины, которая реально
успешно ставит APK на устройство прямо сейчас.

### Автоматическое сообщение оператору при рассинхроне

`Build-Deploy.ps1` (на этой ветке) отслеживает разницу между "ключ только что
создан впервые" (ожидаемо при первой установке) и "ключ уже был локально, но
всё равно не подошёл устройству" (значит разошёлся с тем, что сейчас
реально стоит на устройстве). Во втором случае перед автоматическим
uninstall+reinstall скрипт печатает предупреждение прямо с этими же тремя
шагами переноса ключа — не нужно держать их в голове, они появятся в консоли
в момент, когда действительно нужны.

## 3.5. Надёжность бэкапа прогресса — важное ограничение, не баг

Эксперимент 2026-08-04: временно (см. раздел 9 — это НЕ постоянное изменение,
в `pom.xml` на рабочих ветках/master его быть не должно) добавили в
`android-test-build` execution `set-debuggable`, дающий
`android:debuggable="true"` — это дало рабочий `adb shell run-as forge.app`
для **внутреннего** хранилища приложения (`/data/data/forge.app`).

**Это НЕ чинит бэкап папки прогресса.** Проверено вживую 2026-08-04:
```
adb shell run-as forge.app ls /storage/emulated/0/Android/obb/forge.app
ls: ...: Permission denied
```
даже на debuggable-сборке. Причина: `run-as` запускает процесс вне zygote,
поэтому он не получает тот per-app FUSE-маунт, через который реальный процесс
приложения (запущенный обычным способом) видит свою песочницу под
`Android/obb/<pkg>`/`Android/data/<pkg>`. Это ограничение уровня ОС (scoped
storage), не решается ни правкой скрипта, ни манифеста, ни через `root`
(на этом устройстве `adb root` тоже недоступен — production-сборка Android).

Из-за этого **обычный `adb pull` (от имени `shell`) молча теряет любой файл,
который приложение записало само** — вытягивает только то, что случайно
осталось доступно всем (например, файлы, на которые более ранний `restore`
уже накатил `chmod 777`). `adb pull` при этом не возвращает ошибку — просто
пропускает недоступные файлы. Ровно так 2026-08-04 потерялось сохранение,
специально созданное для проверки бэкапа: в бэкапе оказался только
`forge.log`.

**Защита, которая реально работает (`Test-BackupLooksComplete` в
`Common.ps1`):** после бэкапа скрипт проверяет, есть ли в нём хоть что-то,
кроме `.log`-файлов. Если нет — печатает предупреждение и **останавливается
до install/uninstall**, не давая тихо накатить установку поверх
непрочитанного прогресса. Обойти можно только явным `-Force` (когда точно
известно, что на устройстве и так нечего терять).

**Единственный по-настоящему надёжный способ забрать реальный прогресс** —
вручную, через файловый менеджер с поддержкой Storage Access Framework
(например, "Файлы"): открыть/добавить папку `$dataDir` (раздел 5, п.7 — путь
печатается в консоли) через системный диалог выбора, скопировать содержимое
куда-то ещё. `Backup-ProgressFolder` всё равно пробует `run-as` первым (не
вредит, иногда может сработать на других путях/версиях Android — например на
Android ≤10, где `Get-DeviceAssetsDir` возвращает путь вне obb-песочницы), но
не полагайся на это как на единственную защиту.

### Если всё же нужно повторить debuggable-эксперимент (session-local, см. раздел 9)

Не решает проблему бэкапа (см. выше), но может пригодиться для другой
диагностики (JDWP-дебаг, `run-as` для internal storage). В `pom.xml`, в
профиле `android-test-build`, у execution с `<goal>manifest-merger</goal>`
(id `update-manifest`) сразу после него добавить ещё один `<execution>` того
же плагина `android-maven-plugin`:

```xml
<execution>
    <id>set-debuggable</id>
    <goals>
        <goal>manifest-update</goal>
    </goals>
    <configuration>
        <androidManifestFile>${project.build.directory}/AndroidManifest.xml</androidManifestFile>
        <destinationManifestFile>${project.build.directory}/AndroidManifest.xml</destinationManifestFile>
        <manifest>
            <debuggable>true</debuggable>
            <!-- Обязательно вложено сюда, не отдельным элементом конфигурации -- иначе
            no-op для этого goal, и версия пересчитается по умолчанию из
            android.manifest.versionCodeUpdateFromVersion=true (глобальное свойство
            pom.xml), что даёт INSTALL_FAILED_VERSION_DOWNGRADE против уже
            установленной сборки. Подтверждено на практике 2026-08-04. -->
            <versionCodeUpdateFromVersion>false</versionCodeUpdateFromVersion>
        </manifest>
    </configuration>
</execution>
```

Работает только на `androidManifestFile`/`destinationManifestFile`, указанных
на уже смерженный `target/AndroidManifest.xml` — не на исходный
`src/main/AndroidManifest.xml` (иначе правит закоммиченный файл на диске).
После сессии — раздел 9, шаг 4 (откатить, снять `skip-worktree`).

## 4. Устройство: USB-отладка

1. Настройки → О телефоне → 7 раз тапнуть "Номер сборки" (включает "Для
   разработчиков").
2. Настройки → Для разработчиков → включить "Отладка по USB".
3. Подключить по USB, разрешить на телефоне запрос "Разрешить отладку по
   USB?".
4. Проверить: `adb devices` — статус `device` (не `unauthorized`/`offline`).

Несколько устройств, ни одно не использовалось этим скриптом на этой машине —
`Build-Deploy.ps1` выведет `AMBIGUOUS_DEVICE_SELECTION` + список
`DEVICE\t<serial>\t<model>`, код выхода 2. Перезапустить с `-Serial <serial>`.
Выбор кэшируется в `scripts/.device-state.json` (не в git, per-машина).

## 5. Первый запуск: сборка + деплой

```powershell
powershell -File forge-gui-android/scripts/Build-Deploy.ps1
```

Порядок действий скрипта:

1. Определяет устройство.
2. Находит JDK17 и `mvn`.
3. Скачивает форкнутый `android-maven-plugin:4.6.2` в `.m2` (один раз на
   машину).
4. Маппит `.m2\repository` → `M:` и родительскую папку репозитория → `P:`
   (лимит длины команды cmd.exe на шаге d8).
5. Собирает (`mvn ... -P android-test-build clean verify ...`, 2–5 минут).
6. Переподписывает APK закреплённым keystore (раздел 3).
7. Если на устройстве есть папка прогресса — бэкапит её в
   `scripts/backups/<serial>/<timestamp>/` до установки (`run-as` если
   доступен, иначе `adb pull` — см. раздел 3.5 про ограничения). Две
   проверки, обе останавливают скрипт до install/uninstall, если не
   пройдены (обход — `-Force`):
   - бэкап не похож на пустышку (содержит не только `.log`-файлы) — раздел 3.5;
   - бэкап не подозрительно (>10×) меньше предыдущего для этого устройства
     (защита от бэкапа уже пустого состояния, например после параллельного
     деплоя с другой машины).
8. Ставит APK (`adb install -r -d`). При `INSTALL_FAILED_UPDATE_INCOMPATIBLE`
   — см. раздел 3 (автосообщение) — сносит и ставит заново.
9. Восстанавливает папку прогресса из бэкапа, если она пуста после установки.
10. Подтягивает несмerженные изменения `forge-gui/res/**` текущей ветки.

Скрипт не проверяет совместимость подписи заранее, до сборки — сборка идёт
всегда (если не `-SkipBuild`), несовпадение обнаруживается по факту на шаге
установки (п.8).

## 6. Параметры `Build-Deploy.ps1`

| Параметр | Что делает |
|---|---|
| `-Serial <serial>` | Явно указать устройство |
| `-SkipBuild` | Не собирать, поставить уже собранный APK из `target` |
| `-NoBackup` | Пропустить бэкап/восстановление прогресса целиком |
| `-NoPushRes` | Не подтягивать локальные `res/`-изменения после установки |
| `-BaseBranch <branch>` | Ветка сравнения для `res/`-изменений (по умолчанию `master`) |
| `-Force` | Продолжить, даже если бэкап выглядит пустышкой (только `.log`) или подозрительно меньше предыдущего для устройства (раздел 3.5/5). Использовать только когда точно известно, что на устройстве нечего терять или прогресс изменился легитимно |

## 8. Частые проблемы

- **`adb` не найден** — `platform-tools` не в `PATH`, см. раздел 2.
- **`AMBIGUOUS_DEVICE_SELECTION`** — `-Serial <serial>`.
- **Непонятная ошибка на шаге d8/dex** — обычно длинный путь; смотреть вывод
  `Register-SubstDrive` в логе.
- **`INSTALL_FAILED_UPDATE_INCOMPATIBLE` при уже синхронизированном ключе** —
  значит файл `debug.keystore` разошёлся между машинами; см. раздел 3
  (переотправить + сверить отпечаток).
- **`INSTALL_FAILED_VERSION_DOWNGRADE`** — скрипт передаёт `-d`, но `adb`
  честно предупреждает: `-d` разрешает даунгрейд только для debuggable-пакетов
  — если на устройстве сейчас установлена **не**-debuggable сборка (например,
  бутстрап до появления `set-debuggable` execution в `pom.xml`), `-d` не
  поможет, снос обязателен. Штатно возникать не должно, раз обе стороны
  теперь debuggable; если возникло — вероятно на устройстве сборка с датой из
  будущего (другая машина) либо старая не-debuggable сборка.
- **Предупреждение "Backup ... has no recognizable progress data"** — не
  баг, это защита из раздела 3.5. Не обходить `-Force` не глядя — сначала
  либо забрать прогресс вручную (SAF), либо убедиться, что терять нечего.
- **Устройство Android ≤10 (API ≤29)** — известное ограничение доступа к
  хранилищу, подробности в `CLAUDE.md`. Тестировать на Android 11+.

## 9. Временные (session-local) изменения кода — никогда не должны попасть в прод

Иногда для одной рабочей сессии (отладка, эксперимент, разовая диагностика)
нужно временно поменять что-то в обычном коде проекта — `pom.xml`,
версию/versionCode, флаг в манифесте и т.п. — то, что живёт **не** в
`forge-gui-android/scripts/` и потому не попадает под механизм веток
`tooling-sync`. Пример из практики (2026-08-04): временный
`android:debuggable=true` в `pom.xml` для проверки, поможет ли `run-as`
бэкапу прогресса (не помогло — см. раздел 3.5 — но сама процедура
"внести-поработать-откатить" понадобится ещё).

**Порядок действий:**

1. **Вносим временное изменение** (правим `pom.xml` или что нужно).
2. **Сразу прячем его от git**, пока не забыли:
   ```powershell
   git update-index --skip-worktree forge-gui-android/pom.xml
   ```
   С этого момента `git status`, `git diff`, `git add -A`, `git commit -a` —
   **не видят** этот файл вообще, как будто изменений нет. Это надёжнее, чем
   "просто не забыть не закоммитить": человеческая память подводит, флаг —
   нет. Файл при этом на диске остаётся изменённым — сборка видит правку.
3. **Работаем в сессии как обычно.** Промежуточные коммиты делаем
   как всегда — `git add <конкретные файлы>` — временный файл в них
   физически не попадёт, даже случайным `git add -A`, пока флаг стоит.
4. **По окончании работы — снимаем флаг и откатываем:**
   ```powershell
   git update-index --no-skip-worktree forge-gui-android/pom.xml
   git checkout -- forge-gui-android/pom.xml
   ```
   Проверить `git status` — файл должен быть чистым (не в diff, не untracked).

**Важные оговорки:**

- `--skip-worktree` — свойство **этой конкретной рабочей копии** (не
  синхронизируется через git, не пушится, не видна на второй машине). На
  каждой машине, где повторяется такая сессия, флаг ставится заново.
- Пока флаг стоит, `git pull`/`merge`/`checkout <другая ветка>`, которые по
  идее должны обновить этот файл, могут промолчать и **не обновить его** —
  git считает файл "как будто не изменился, трогать не буду". Если в проекте
  реально что-то поменяли в `pom.xml` пока у тебя стоит `skip-worktree` — снять
  флаг *до* pull/merge/checkout, иначе получишь рассинхрон с историей молча.
- Список файлов с флагом сейчас: `git ls-files -v | grep '^S'` (заглавная `S`
  = skip-worktree).
- Если нужно быстро повторить именно debuggable-эксперимент из раздела 3.5 —
  сам XML-блок для `pom.xml` (профиль `android-test-build`, execution
  `set-debuggable`) описан там же; скопировать оттуда, а не переизобретать.
